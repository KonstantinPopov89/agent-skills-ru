# Воспроизводимая проверка кассовых агрегатов

CLI проверяет явно заданный контракт и пересчитывает предоставленные строки. Он не определяет смысл полей по их названиям и не доказывает полноту потока парка, корректность отдельных чеков, личность сотрудника или причинность изменений.

```sh
python3 scripts/check_cashier_data.py \
  --input examples/rows.json \
  --spec examples/spec.json \
  --output check-result.json
```

Python 3.10+, только стандартная библиотека. Каталог output должен существовать. Вход и spec открываются только на чтение; совпадение output с ними, включая symlink/hardlink, запрещено. Output перезаписывается по явно переданному адресу. В JSON-результате нет времени запуска, имен учетных записей и исходных значений нечисловых ошибок. Есть SHA-256 исходных байтов input/spec; одинаковые байты и версия CLI дают одинаковый output.

## Спецификация

[Учебная спецификация](../examples/spec.json) описывает только [вымышленный экспорт](../examples/rows.json). Для своих данных заново подтверди поля, охват, единицы и допущения. Дополнительные ключи spec отклоняются.

| Поле | Обязательное содержание |
|---|---|
| `schema_version` | `1` |
| `input` | `{"format":"json_array"}` либо `{"format":"csv","delimiter":";"}` |
| `source` | Непустые `description` и массив ссылок `evidence` |
| `assumptions` | Явный массив допущений; пустой массив допустим |
| `scope` | `kind`: `observed_export_only` или `declared_dataset`; `completeness`: `confirmed`, `partial`, `unverified`; массив `evidence` |
| `granularity` | Непустое `description`; `contract_status`: `confirmed`, `assumed`, `unknown`; массив `evidence` |
| `fields` | Шесть различных исходных имен для `date`, `account`, `gross`, `returns`, `net`, `receipts` |
| `date_format` | Один из `%Y-%m-%d`, `%d.%m.%Y`, `%d/%m/%Y`, `%m/%d/%Y` |
| `money` | Валюта `currency` в виде трех заглавных латинских букв и общая единица `unit` для gross/returns/net |
| `period` | `start` и `end` в ISO, обе границы включены; boolean `assert_all_rows_within` |
| `include_accounts` | Необязательный массив точных уникальных строк. Отсутствует: без фильтра. `[]`: пустой выбор |
| `contract` | Объект явных проверяемых контрактов; `{}` допустим |
| `mean_decimal_places` | Необязательное целое от 0 до 24; по умолчанию 6 |

`confirmed` для охвата или гранулярности требует непустого `evidence`. CLI проверяет наличие ссылки, но не подлинность доказательства. Для `observed_export_only` полный охват означает все строки предоставленного массива, а не весь upstream-отчет или парк. Если заявленная выборка получена частично, укажи `partial`; нельзя повысить ее до полного набора наличием файла. Для `declared_dataset` полноту целевого набора подтверждают отдельно.

Контракты включаются только явно. Отсутствующий контракт или `null` означает `NOT_APPLICABLE`, а не PASS:

```json
{
  "gross_minus_returns_equals_net": {
    "asserted": true,
    "tolerance": "0.01",
    "evidence": ["Ссылка на согласованное определение равенства в этой единице"]
  },
  "receipts": {
    "integer": true,
    "nonnegative": true,
    "evidence": ["Ссылка на определение счетчика"]
  },
  "unique_key": {
    "fields": ["account", "date"],
    "asserted": true,
    "evidence": ["Ссылка на контракт уникальности, а не только наблюдение в этом файле"]
  }
}
```

- Допуск равенства задан в той же единице, что gross/returns/net; `abs(gross - returns - net) <= tolerance`.
- Уникальный ключ состоит из логических имен `fields`, а не исходных названий колонок. Совпадение ключа дает FAIL только при заявленном контракте. Неизвестный компонент ключа дает UNKNOWN.
- Без контракта уникальности одинаковые значения шести сопоставленных полей остаются `CANDIDATE_ONLY`. Ни одна строка не удаляется; совпадение не доказывает дубль операции.
- Ограничения целочисленности и неотрицательности receipts включаются независимо. Они не распространяются на произвольные величины или деньги.

## Парсинг, период и охват

JSON должен быть массивом объектов; envelope, JSONPath, XLSX, JSONL и вложенные поля не поддерживаются. Повторяющиеся ключи JSON запрещены. CSV должен иметь уникальную непустую шапку и одинаковое число полей в каждой записи. Кодировка UTF-8, BOM допустим. Дополнительные исходные колонки сохраняются во входе, но не участвуют в вычислениях.

Числа читаются как `Decimal`, без промежуточного float. Поддерживаются знак, десятичная точка и экспонента. Пробелы, разделители тысяч, десятичная запятая, bool, массив и объект не угадываются и дают FAIL числовой проверки. Отсутствие, null, пустая ячейка и NaN/Infinity дают UNKNOWN и не превращаются в ноль. Для ограничения ресурсов допускается до 256 значащих цифр, модуль экспоненты и десятичного порядка не больше 1000; превышение дает FAIL с причиной. Арифметика сумм выполняется с достаточной для этих ограничений точностью.

Дата должна точно соответствовать формату, включая ведущие нули; неправильная дата дает FAIL, отсутствующая дает UNKNOWN. Период всегда фильтрует строки. При `assert_all_rows_within=true` строка вне периода дополнительно нарушает контракт; при `false` это обычное исключение. Отсутствующий в данных день выводится для осмотра, но не считается доказательством пропуска выгрузки или простоя.

Каждая строка попадает ровно в одну группу:

1. `included`: дата внутри периода, учетная запись проходит заданный фильтр.
2. `excluded`: хотя бы один критерий достоверно исключает строку, даже если другой неизвестен.
3. `unclassifiable`: исключение не доказано, хотя бы один необходимый критерий неизвестен.

Проверяются сохранность числа строк и равенство известных сумм/числа неизвестных по разделам исходному массиву. Перечислены номера строк каждой группы. При фильтре отсутствующая учетная запись делает членство неизвестным. Без фильтра account пропуск диагностируется, но сам по себе не исключает денежную строку. Структурные, числовые и контрактные проверки проводятся по всем входным строкам, включая исключенные; итоговые суммы и weighted mean относятся к выборке.

## Итоги и статусы

Для каждой из четырех величин и каждой группы есть `known_sum`, `total`, `known_count`, `unknown_count`, `row_count`, `completeness`. Известная часть не называется полным итогом: при неизвестном значении `total=null`. В пустом множестве сумма равна нулю, но `completeness=empty`; пустая выборка не дает успешного содержательного заключения.

`selected_totals` дополнительно учитывает неизвестное членство. Если есть `unclassifiable`, выбранный итог равен `null`, даже когда все уже включенные значения известны. `membership_unknown_rows` показывает число строк, которые могут изменить охват; их деньги видны в отдельной группе, но не подмешиваются в итог.

Среднее: `sum(net) / sum(receipts)`, включая строки возврата с нулем новых чеков. Средние по строкам не усредняются. В output сохранены числитель и знаменатель; округляется только отношение, `ROUND_HALF_EVEN`, до заданного количества знаков. Неизвестные суммы/членство дают UNKNOWN. Нулевой знаменатель или пустая выборка дают `NOT_APPLICABLE` и `value=null`; возврат без новой продажи не считается бизнес-ошибкой.

- `status` относится только к `status_scope` и заявленным проверкам: FAIL при доказанном нарушении; UNKNOWN при незакрытой проверке внутри охвата; иначе PASS. `partial`/`unverified` охват или непроверенная гранулярность не могут дать итоговый PASS.
- `arithmetic_status` отдельно показывает проверки данных и вычислений без утверждения полноты источника и гранулярности. Применимые UNKNOWN внутри этих проверок остаются UNKNOWN.
- `observed_export_only` может получить ограниченный PASS, если вся предоставленная выборка и заявленные проверки закрыты. Это не глобальный вывод о бизнесе.
- `global_business_status` всегда `NOT_ASSESSED`. `external_scope_validation` отмечает `NOT_TESTED` для полного потока парка, личности сотрудника, причинности и отдельных транзакций. Они находятся вне проверки, а не становятся выдуманными ошибками корректного экспорта.
- `checks` содержит status, область проверки, actual/expected и детали нарушений/неизвестного. `locator.row` считается с 1: элемент JSON-массива или запись данных CSV без шапки, не физическая строка многострочного CSV. Значения персональных полей не выводятся.

Коды завершения:

| Код | Значение |
|---|---|
| `0` | Вычисление завершено без доказанного FAIL; результат может быть UNKNOWN или содержать NOT_APPLICABLE. Код 0 сам по себе не означает PASS |
| `1` | Есть доказанный FAIL проверки данных или заявленного контракта |
| `2` | Невалидная конфигурация/структура ввода, неподдержанный формат, ошибка чтения/записи или попытка записать поверх input/spec |

Валюта и общая единица объявляются оператором. CLI не распознает смешанные единицы, не конвертирует валюту, не сверяет банк/ОФД/кассовый журнал и не делает выводов о гостях, сотрудниках или выручке всего парка по одному полю account.

## Известная схема development-примера

| Логическая роль | Поле известного экспорта |
|---|---|
| account | `GRP` |
| date | `GRP_2`, `%d.%m.%Y` |
| gross | `MADE_MONEY` |
| returns | `RETURN_MONEY` |
| net | `MONEY` |
| receipts | `COUNT_CHEK` |

`AvgCheck` и `AvgCheckTotal` не используются как источник вычисляемого среднего; net/receipts пересчитываются независимо. Пример не объявляет `account + date` уникальным ключом. Для нового парка либо другой выгрузки эту схему сначала подтверждают; счетчики не переименовывают в гостей или людей.
